# テスト方針 {#top}

CSR の Web アプリケーションにおけるテストのあり方を示します。

## テスト方針の概要 {#test-policy}

AlesInfiny Maris OSS Edition では、バックエンドの .NET アプリケーションと、フロントエンドの TypeScript アプリケーションを対象にテストします。
各アプリケーションのテストの詳細は、以下を参照してください。

1. [バックエンドアプリケーションのテスト](backend-application/index.md)
1. [フロントエンドアプリケーションのテスト](frontend-application/index.md)

## テストレベル {#test-level}

テストで確認する内容に合わせて、テストレベルを定義することが一般的です。
本稿では、単体テストフェーズの UT0 、 UT1 と、結合テストフェーズの ITa を定義します。
これ以外のテストレベルは、実行方法などを解説しません。

### 単体テストフェーズ {#unit-test-phase}

フロントエンドアプリケーションとバックエンドアプリケーションを、それぞれ個別にテストするフェーズです。
静的テストでは、静的解析ツールによる自動解析とあわせて、ソースコードをレビューします。
それ以外のテストは、 CI ツールに組み込んで短時間で実行できるように作成します。

#### UT0 {#ut0}

アプリケーションを構成する部品が、設計どおりに実装されているか確認するテストです。
部品単体を対象とします。
部品の外部に依存する箇所はモック化します。

| 対象           | テスト種別 | 内容                                                                                                               |
| -------------- | ---------- | ------------------------------------------------------------------------------------------------------------------ |
| バックエンド   | 静的テスト | 静的解析ツールによる解析とレビューにより、ソースコード中の不具合の原因となる記述や規約違反を検出                   |
| バックエンド   | 単体テスト | クラス単位で、論理設計書どおりに実装されていることを検証                                                           |
| フロントエンド | 静的テスト | 静的解析ツールによる解析とレビューにより、ソースコード中の不具合の原因となる記述や規約違反、型の誤りを検出         |
| フロントエンド | 単体テスト | モジュール、コンポーザブル、ストア、サービス、モデル、スキーマの単位で、画面設計書どおりに実装されていることを検証 |

#### 機能内結合テスト ( UT1 ) {#ut1}

UT0 が完了した部品を結合し、機能単位の仕様が実現できているか確認するテストです。

| 対象           | テスト種別           | 内容                                                                                                                                     |
| -------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| バックエンド   | Web API テスト       | HTTP メソッド単位で、論理設計書どおりに実装されていることを検証                                                                          |
| フロントエンド | コンポーネントテスト | コンポーネントの設計単位で、 UI 、ロジック、子コンポーネントを結合したコンポーネントの描画と操作時の動作が、仕様を満たしていることを検証 |
| フロントエンド | 画面テスト           | 画面単位で、 UT0 で検証した部品を結合した画面の描画と操作時の動作が、レイアウト（見た目）を含めて設計書どおりであることを検証            |
| フロントエンド | 画面遷移テスト       | 画面遷移単位で、共通機能（ルーター、グローバル状態）と結合し、画面遷移を伴うイベントが発火して設計どおりに処理されることを検証           |

### 結合テストフェーズ {#integration-test-phase}

単体テストフェーズで検証した機能を結合し、システムが要求仕様どおりに動作するか確認するフェーズです。

#### 機能間結合テスト ( ITa ) {#ita}

フロントエンドアプリケーションとバックエンドアプリケーションを結合し、ユースケース単位で動作を確認するテストです。

| 対象                         | テスト種別 | 内容                                                                                                 |
| ---------------------------- | ---------- | ---------------------------------------------------------------------------------------------------- |
| フロントエンド、バックエンド | E2E テスト | ユースケース単位で、画面から DB まで一気通貫で動かし、要求されたユースケースを網羅していることを検証 |

#### 自動 E2E テストの対象 {#e2e-targets}

自動 E2E テストは実装、実行、保守のコストが高いため、想定どおり動作しなかった場合の業務上の影響が大きいユースケースに絞って自動化します。
具体的には、以下のユースケースを対象とします。

- **ハッピーパス**: 最も一般的なユースケース（例: 会員が商品を購入する）
- **ネガティブパス**: 異常系のうち、想定外の動作をした場合にリスクが高いユースケース（例: 決済サービスの不通により購入がエラーになる）

それ以外のユースケースは、手動で操作して検証します。

自動 E2E テストの設定方法や実装方法は、 [E2E テストの設定](../../../guidebooks/how-to-develop/csr/vue-js/e2e-test-settings.md) を参照してください。
