# テスト方針 {#top}

CSR の Web アプリケーションにおけるテストのあり方を示します。

## テスト方針の概要 {#test-policy}

AlesInfiny Maris OSS Edition では、バックエンドの .NET アプリケーションと、フロントエンドの TypeScript アプリケーションを対象にテストします。
各アプリケーションのテストの詳細は、以下を参照してください。

1. [バックエンドアプリケーションのテスト](backend-application/index.md)
1. [フロントエンドアプリケーションのテスト](frontend-application/index.md)

## テストレベル {#test-level}

テストで確認する内容に合わせて、テストレベルを定義することが一般的です。
本稿では、単体テストフェーズと結合テストフェーズに含まれる以下のテストレベルを定義します。
このうち ITb 以降のテストレベルについては、実行方法などを解説しません。

### 単体テストフェーズ {#unit-test-phase}

フロントエンドアプリケーションとバックエンドアプリケーションを、それぞれ個別にテストするフェーズです。
いずれのテストも、コード分析ツールや自動テストツールで自動実行します。
テストは、 CI ツールに組み込んで短時間で実行できるように作成します。

#### UT0 {#ut0}

アプリケーションを構成する部品が、設計通りに実装されているか確認するテストです。
部品単体を対象とします。
部品の外部に依存する箇所はモック化します。

| 対象           | テスト種別 | 内容                                                                                                             |
| -------------- | ---------- | ---------------------------------------------------------------------------------------------------------------- |
| バックエンド   | 静的テスト | ソースコードを解析し、不具合の原因となる記述や規約違反を検出                                                     |
| バックエンド   | 単体テスト | クラス単位で、論理設計書通りに実装されていることを検証                                                           |
| フロントエンド | 静的テスト | ソースコードを解析し、不具合の原因となる記述や規約違反、型の誤りを検出                                           |
| フロントエンド | 単体テスト | モジュール、コンポーザブル、ストア、サービス、モデル、スキーマの単位で、画面設計書通りに実装されていることを検証 |

#### 機能内結合テスト ( UT1 ) {#ut1}

UT0 が完了した部品を結合し、機能単位の仕様が実現できているか確認するテストです。

| 対象           | テスト種別           | 内容                                                                                                                       |
| -------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| バックエンド   | Web API テスト       | HTTP メソッド単位で、論理設計書通りに実装されていることを検証                                                              |
| フロントエンド | コンポーネントテスト | コンポーネントの設計単位で、 UI 、ロジック、子コンポーネントを結合したコンポーネントが成立し、仕様を満たしていることを検証 |
| フロントエンド | 画面テスト           | 画面単位で、モジュールを結合した画面が、レイアウト（見た目）を含めて設計書通り成立していることを検証                      |
| フロントエンド | 画面遷移テスト       | 画面遷移単位で、共通機能（ルーター、グローバル状態）と結合し、画面遷移を伴うイベントが発火して設計通り処理されることを検証 |

### 結合テストフェーズ {#integration-test-phase}

単体テストフェーズで検証した機能を結合し、システムが要求仕様どおりに動作するか確認するフェーズです。

#### 機能間結合テスト ( ITa ) {#ita}

ユースケース単位でフロトエンドアプリケーションとバックエンドアプリケーションの間の結合を検証し、要求されたユースケースが網羅されていることを確認するテストです。

| 対象                         | テスト種別 | 内容                                                                                                 |
| ---------------------------- | ---------- | ---------------------------------------------------------------------------------------------------- |
| フロントエンド、バックエンド | E2E テスト | ユースケース単位で、画面から DB まで一気通貫で動かし、ユースケースカバレッジを網羅していることを検証 |

### 自動 E2E テストの対象 {#e2e-targets}

E2E テストのうち、重要なユースケースに絞って自動化します。
自動 E2E テストは実装、実行、保守のコストが高いためです。
自動化の対象は、想定どおり動作しなかった場合の業務上の影響が大きいユースケースです。

- **ハッピーパス**: 最も一般的なユースケース（例: 会員が商品を購入する）
- **ネガティブパス**: 異常系のうち、想定外の動作をした場合にリスクが高いユースケース（例: 決済サービスの不通により購入がエラーになる）

設定方法や実装方法は、 [E2E テストの設定](../../../guidebooks/how-to-develop/csr/vue-js/e2e-test-settings.md) を参照してください。
